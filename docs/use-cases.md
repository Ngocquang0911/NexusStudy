# NEXUS STUDY — Use Case Specification

**Document status:** Based on the current repository implementation
**Audience:** Product, design, development, QA, and academic reviewers
**Product:** A collaboration platform for student workspaces, group projects, and study

## 1. Purpose and scope

This document describes the use cases visible in the current NEXUS STUDY application and backend. It distinguishes implemented behavior from features that appear in product plans but are not yet exposed as complete workflows.

The application is organized around workspaces (also called Spaces). Members use them to coordinate tasks, communicate, share documents, make decisions, and review contribution. The system also provides account management, subscription entitlements, AI study assistance, and a separate administrator area.

## 2. Actors and role model

### 2.1 Actors

| Actor                                  | Description                                                                                                                                          |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Visitor**                      | A person who has not signed in. Can register, verify an email address, or log in.                                                                    |
| **Student / Authenticated user** | A signed-in user who can use personal account features and participate in workspaces according to membership and plan.                               |
| **Workspace Owner**              | The owner of one specific workspace. Has workspace-level administrative permissions, including deleting that workspace.                              |
| **Workspace Leader**             | A workspace member with operational permissions for selected management actions.                                                                     |
| **Workspace Member**             | An accepted member who participates in tasks, chat, polls, documents, and evaluations according to authorization rules.                              |
| **Advisor**                      | A workspace role available for academic or advisory participation. Exact permissions depend on the operation; it does not imply system-admin access. |
| **System Administrator**         | An account with the system role `ADMIN`. Can use the separate admin area to review system data and manage account roles and plans.                 |
| **System**                       | NEXUS STUDY backend, database, authorization middleware, notification services, realtime services, and scheduled jobs.                               |
| **AI Provider / Email Provider** | External providers called by backend services when configured. They do not receive direct browser-side credentials.                                  |

### 2.2 Two independent role dimensions

System roles and workspace roles are different:

- **System role:** `STUDENT`, `LECTURER`, or `ADMIN`; applies to the account across the application.
- **Workspace role:** `OWNER`, `LEADER`, `MEMBER`, or `ADVISOR`; applies only inside a particular workspace.

An account can be a system administrator and still have no membership in a given workspace. Being an administrator does not automatically grant access to that workspace's private content or the right to delete it. Only the Owner of the selected workspace can use the Owner-only delete operation.

## 3. Authorization and subscription rules

- Authentication is required for private account, workspace, task, chat, poll, document, evaluation, notification, and AI operations.
- Workspace access is checked on the backend for the specific workspace or resource; hiding a control in the UI is not authorization.
- Owner/Leader capabilities are checked separately from ordinary membership where the operation requires management rights.
- A deleted workspace cannot be used for normal collaboration. Archive access is a separate, limited permission based on the member snapshot recorded at deletion.
- An invitee becomes an official member only after accepting the invitation. A pending invite alone does not grant workspace or deleted-archive membership.
- Workspace-wide entitlements such as additional chat channels and pin limits use the workspace owner's plan. Account-scoped features such as custom reminders and contribution reports check the acting account's plan.
- Current plan limits include Free: up to 3 workspaces, 4 pinned messages, 90-day document retention, and standard reminders; Premium: no configured workspace-count cap, 50 pinned messages, 365-day document retention, and custom reminder schedules. The reminder limit field is represented as a maximum in the plan configuration; users should not interpret it as a different reminder policy unless confirmed by the UI.

## 6. Use cases for System Administrator

| ID               | Use case                          | Primary actor        | Preconditions and result                                                                                                                                                                          |
| ---------------- | --------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **UC-A01** | Access the admin area             | System Administrator | Actor is authenticated and the backend confirms system role `ADMIN`. Non-admin accounts are denied.                                                                                             |
| **UC-A02** | View system overview              | System Administrator | Admin views aggregate user, workspace, task, content, and growth metrics, plus selected recent activity. The overview does not provide private message content.                                   |
| **UC-A03** | Search and filter user accounts   | System Administrator | Admin searches or filters the account directory by supported fields and reviews account metadata.                                                                                                 |
| **UC-A04** | Change a user's system role       | System Administrator | Admin selects an eligible account and role and supplies a reason. The system validates the role, prevents unsafe self-demotion/last-admin demotion, saves the change, and writes an audit record. |
| **UC-A05** | Change a user's subscription plan | System Administrator | Admin selects Free or Premium and supplies a reason. The system updates the account plan and records an audit entry.                                                                              |
| **UC-A06** | Review active workspaces          | System Administrator | Admin searches and views basic information about active workspaces and their owners. This is not equivalent to membership or permission to use private workspace content.                         |

### Administrator exclusions

The current admin use cases do **not** grant a system administrator permission to:

- Delete any user's workspace through the Owner deletion flow.
- Impersonate a workspace member.
- Read private workspace messages or download workspace documents without normal membership.
- Change Owner/Leader/Member roles inside a workspace merely because the actor is a system Admin.

Any future moderation or policy-enforcement workflow should be specified separately, with explicit authorization, reason capture, and audit requirements.

## 7. Shared rules for deleted workspaces

1. The workspace Owner is authorized to delete only their own active workspace.
2. Deletion immediately blocks normal workspace operations such as chat, tasks, polls, and realtime participation.
3. At deletion, the system snapshots official members. Pending invitees and outsiders are excluded.
4. The Owner and snapshotted members may use archive-only document access during the five-day retention period.
5. Archive permission is not current workspace membership and does not allow editing, creating, voting, chatting, inviting, or managing roles.
6. After the deadline, archive reads/downloads are denied and scheduled purge removes workspace-scoped data.
7. Purge must not delete user accounts or data belonging to another workspace. A physical file is removed only when it is not referenced elsewhere.
8. A system Admin receives no archive permission unless they were themselves in the deletion-time member snapshot.

## 8. Implementation status and documentation boundaries

The use cases above describe current routes and service behavior where implemented. The repository also contains a broader product specification with proposed or future workflows. The following distinctions are important when using this document for a formal report:

- The current backend has authentication, email verification, profile/password changes, workspace invitations, role checks, tasks, task deadlines/reminders, chat, documents, polls, contribution evaluations, AI endpoints, notifications, a system-admin area, and a five-day deleted-workspace archive.
- The current calendar view should not be interpreted as proof of a separate meeting/event authoring subsystem; the implemented deadline model is task-centered.
- AI task suggestions require Premium. Other AI endpoints use authenticated workspace/document authorization and may still fail explicitly if provider configuration is unavailable.
- Some UI or product-plan ideas (for example Pomodoro, full multi-workspace chat, general calendar events, or complete external integrations) are not described as implemented workflows unless a current backend route and permission flow support them.
- The five-day deleted-workspace archive is distinct from the normal document-retention periods attached to documents in active workspaces.

## 9. Suggested end-to-end scenarios for QA

1. Register, verify an email, log in, update a profile, and change a password.
2. Create a workspace, invite another user, accept the invitation, and confirm both users can access only that workspace.
3. Verify Free plan workspace, pin, and document retention limits; verify Premium-only custom reminders and task suggestions.
4. Create a task, assign it to a workspace member, set a deadline, update status, and confirm feedback notification delivery.
5. Create a private channel and verify that an unselected workspace member cannot read or send messages there.
6. Upload a document, request an AI summary, and verify that a user outside the workspace cannot access the document or AI operation.
7. Create a poll, vote once, and verify duplicate or unauthorized voting is rejected.
8. Submit evaluations and verify report access is limited to permitted Owner/Leader accounts and plan eligibility.
9. Verify an Admin can manage system roles/plans with a reason but cannot delete or access a workspace solely by being Admin.
10. Delete a workspace as its Owner; verify invitations are cancelled, official members receive notices, normal operations are blocked, and only snapshotted members can access eligible archive documents until expiry.
11. Purge an expired workspace and verify a different workspace with overlapping members and any shared file remains intact.
